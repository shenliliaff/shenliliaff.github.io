    智谱把 28 层跑了两遍，然后说这等于一个 2 万亿到 3 万亿参数的模型模型发布
    • 11-23 智谱发布 GLM-5.4：750B 基座不变，把第 27–54 层共 28 层权重共享跑两遍，官方称智能水平相当于 2 万亿—3 万亿参数模型
    • 唯一量化证据是同架构 30B 的等参对照：训练算力只多约 10%，AIME25 19.17→30.42、GPQA-Diamond 47.58→56.26，平均输出长度反降 2%–14.9%
    • 即日起向 GLM Coding Plan 全量用户开放，接入 ZCode、Trae、WorkBuddy、Qoder，V2/V3/团队版额度提到 1.5 倍；非高峰 200 token/s、高峰 70–80 token/s
    • API 要等安全评估，权重「计划开源」但须先完成安全加固，两项均无时间表；官方预告下一个模型规模显著更大
    • 官方自曝短板：容易陷入过长的「马拉松式思考」循环；GLM-5.4 自身未公布任何跑分，两家第三方追踪站当晚均未收录
    完整摘要

    2026 年 11 月 23 日，智谱（Z.ai）通过官方技术博客与官方公众号发布新一代旗舰模型 GLM-5.4，称其为第一代采用 Loop Transformer 架构的旗舰模型。做法是不加参数、加深度：把 GLM-5 基座第 27 至 54 层共 28 层权重共享，在一次前向里跑两遍，第二遍在第一遍的隐状态上继续推演。基座规模 750B（官方口径约 7500 亿参数），官方称其智能水平达到 2 万亿至 3 万亿参数级模型的效果，但没有公布 GLM-5.4 本身的任何跑分。能查到的量化数据全部来自一个同架构 30B 模型的等参对照——参数完全相同、训练算力只多约 10%：AIME25 从 19.17 升到 30.42、GPQA-Diamond 47.58→56.26、AA-LCR 40.33→47.67、MMLU-Pro 71.65→75.05、IFBench 50.20→53.47，同时平均输出长度反而降了 2%–14.9%，官方解释是一部分推理从 token 流搬进了循环带来的额外深度。为压住部署成本做了三处工程改动：每轮独立的逐 token 门控（第一轮保守写回、第二轮放开）、KV Cache 跨轮共享加滑窗独立、稀疏注意力索引直接复用第一轮结果；官方称在 1M 上下文下相对 GLM-5.3 的部署成本增幅「可控」，非高峰最高 200 token/s、高峰 70–80 token/s。可用性上，即日起向 GLM Coding Plan 全量用户开放，同步上线 ZCode、Trae、WorkBuddy、Qoder 等编码平台，Coding Plan V2/V3/团队版额度提升至 1.5 倍；API 需等安全评估完成，权重「计划以负责任的方式开源」但要先做完安全加固，两项均未给时间表。模型对比的胜平负来自 200 个真实场景的编程实战评测：对 GLM-5.3 是 51.1%/25.7%/23.1%，对 Kimi K3.1 Pro 是 41.8%/26.9%/31.3%，对 DeepSeek-V4.1-Flash-1017 是 36.6%/30.2%/33.2%。官方主动写出的短板是模型容易陷入过长的「马拉松式思考」循环，但称这种反复自省确实能让准确率超出其参数规模。同篇博客预告下一个模型「规模显著更大，很快见面」。留白：2T-3T 是自评、无第三方复现，AI Release Tracker 与 Artificial Analysis 当晚均未收录该模型，API 与权重都还没有确切日期。

    OpenAI 和思科做了面「盾」：补丁还没打上的机器，先自己扛住安全对齐
    • 11-23 OpenAI 与思科发布开源项目 Shirudo：eBPF 运行时，不重启、不改源码就把漏洞利用路径堵住，等正式补丁铺开
    • 公开唯一实测是 Java4Shell：Codex 自动生成 Java 字节码注入运行中的 Elasticsearch 9.5.5，拦下 Base64 覆写型 exploit
    • 签名 + TPM：shield 由内核校验签名后加载，每次开机扩展 TPM 寄存器，运维可离线核验这台机器装了什么
    • 思科给出的理由很直接——「平均利用时间已经变成负数」，漏洞在被披露前就被利用，而补丁铺满要几周甚至几个月
    • 硬留白：README 自标 pre-release，生产要求带 shirudo 内核补丁的 Linux 与 TPM 2.0；性能开销未公布，riscv64 未验证
    完整摘要

    2026 年 11 月 23 日，OpenAI 与思科（Cisco）联合发布开源项目 Shirudo（日语「シールド」，盾），定位是一个帮助运维团队在补丁铺开之前保护正在运行的生产系统的运行时安全平台。技术底座是 eBPF：不重启、不改源码，在系统调用的关键点装一段小程序，把漏洞利用要走的那条路堵掉。Shirudo 把这类小程序叫 shield，在 README 里叫 upatch（签名的微补丁），由运维侧签名后打成 .bee 包推到 OCI 仓库，目标机一次性拉取，加载前由内核校验签名，加载或卸载都会扩展一个每次开机重置的 TPM 寄存器，运维可以离线核验这台机器上到底装了什么。它没有常驻守护进程，只有一个一次性 CLI，启动时的守卫从 initrd 里挂上。公开的唯一实测是 Java4Shell（OpenJDK 的一个新漏洞）：用 Codex 当控制面，自动写出复现器、选定缓解点、生成一段 Java 字节码，注入到正在运行的 Elasticsearch 9.5.5 进程的 java.util.Base64$Decoder.decode0 上，随后 exploit 被拒，日志里留下「Base64 guard rejected candidate: length=65, padding=1, remainder=1」。思科 Isovalent 团队（Thomas Graf、Liz Rice 署名）给出的理由是「平均利用时间已经变成负数」——越来越多漏洞在被公开披露之前就已经被人利用了，而一个关键修复从写出来到铺满大多数系统还要几天、几周甚至几个月。思科方面说 Shirudo 是 Tetragon 的重写版（Tetragon 2022 年由 Isovalent 开源，也是思科产品里 Live Protect 能力的地基），关键改动是「不再把智能体限制在为人设计的策略语言里，让它们用母语说话：代码」，因此「故意不做配置 DSL」。留白很硬：仓库 README 自己写着 shirudo is pre-release，生产环境要求一个带 signed-loader ABI 和 shirudo 内核补丁的 Linux 内核，外加 TPM 2.0——也就是说，这个「保护你还没打补丁的系统」的工具，前提是你先给自己的内核打了补丁；riscv64 的验证还在等；性能开销官方两份公告都没提；截至北京时间 11 月 24 日早间仓库 190 star、13 fork、30 个 open issue，代码 BSD 2-Clause、BPF 程序 BSD 与 GPL 双许可，12 月 15 日有一场技术深潜 webinar。
