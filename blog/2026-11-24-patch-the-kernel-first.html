一个专门保护「还没来得及打补丁」的机器的工具，要求你先打补丁

人工智能约 1320 字大约 4 分钟...

一个专门保护「还没来得及打补丁」的机器的工具，要求你先打补丁

美国时间 11 月 23 日，OpenAI 和思科一起放了个开源项目，叫 Shirudo。日语里是「盾」。

我第一眼看到这名字，想到的是小区门口那道升降杆。杆子拦车，不拦人。这面盾拦的也不是人，是漏洞利用——在补丁还没发下来、或者发下来了还没铺到每一台机器上的那段时间里，让攻击打不进去。

运维这行有个老规矩：公告一出，先数自己有多少台机器受影响。数字一出来，心里先凉一半。补丁要测，测完要排期，排期要等窗口，窗口一般在下周三凌晨两点。中间这几天，机器就那么开着，谁也不睡。

思科的 Thomas Graf 和 Liz Rice 在博客里写了一句话，是全文最狠的：平均利用时间已经变成负数。

负数是什么意思。意思是很多漏洞，黑客比公告先动手。你还没看见公告，人家的脚本已经在跑了。等到你排上那个凌晨两点，事情可能已经发生完了。

所以 Shirudo 的做法是插在中间。它用 eBPF——Linux 里那个能在内核的关键点上跑小程序的机制——不改源码、不重启，把漏洞利用必须走的那条路堵掉。他们把这种小程序叫 shield，仓库里叫 upatch，签名的微补丁。运维这边签好名，打成包推到 OCI 仓库，目标机自己一次性拉下来，加载前内核先验签名，装上或卸掉都会往一个每次开机重置的 TPM 寄存器里记一笔，事后可以离线核对这台机器到底装过什么。整个东西没有常驻进程，只有一个一次性命令行。

公开的实测只有一个，但足够具体。用的是 Java4Shell，OpenJDK 里一个新漏洞。他们让 Codex 当调度，自己写复现器、自己挑缓解点、自己生成一段 Java 字节码，挂到正在跑的 Elasticsearch 9.5.5 进程上，位置是 java.util.Base64$Decoder.decode0。然后去打。没打进去。日志里留下这么一行：

Base64 guard rejected candidate: length=65, padding=1, remainder=1, alphabet=standard

到这儿都挺漂亮。然后我去翻了仓库的 README。

README 里明明白白写着：shirudo is pre-release。生产环境的要求是——一个带 signed-loader ABI 的 Linux 内核，加上 shirudo 自己的内核补丁，再加一块 TPM 2.0。

也就是说，这个用来保护「你还没打补丁的系统」的东西，前提是你先给自己的内核打个补丁。

盾是新的，门是旧的。

这不是他们藏着掖着，README 第一屏就写了，官方博客也没回避。但这个弯绕得实在有水平：一个卖给「来不及」的人的解决方案，自己先要过一遍「来不及」的那道关。装不上内核补丁的机器，还是装不上这面盾。riscv64 的验证还在等，性能开销两份公告一个字没提。

它的来历倒是有意思。Shirudo 是 Tetragon 的重写版，Tetragon 是 Isovalent 2022 年开源的 eBPF 安全项目，现在是思科产品里 Live Protect 的地基。Isovalent 早被思科收了，所以这一整套东西姓思科，而 OpenAI 出的是脑子和调度。10 月 6 日，两个作者 Daniel Borkmann 和 John Fastabend 就已经在布拉格的 Linux Plumbers 会议上讲过它，比这次联合发布早了一个多月。

重写的理由，他们讲得挺直白。以前的智能体被塞进给人用的策略语言里，像让一个会说人话的人去填表，格子还填不下。现在的做法是不填了，直接写代码，内核自己验。「故意不做配置 DSL」——这是原话，理由是智能体对代码的适应能力远好于对抽象概念的适应能力。

截至今天早上，这个仓库 190 个 star，13 个 fork，30 个 open issue，许可证 BSD 2-Clause，BPF 程序 BSD 和 GPL 双许可。12 月 15 日有一场技术详解的线上会。一个 pre-release 的东西，一周内不会有人拿它上生产，这很正常。

我关掉页面的时候想的是另一件事。补丁和盾，本来是同一件事的两头：一头是根治，一头是拖时间。现在一头跑得太快，另一头根本追不上，中间就空出一段路。这段路上现在开始有人摆摊了。

那个值班的人今晚大概还是两件事：先想办法给内核打补丁，再用盾去保护那些来不及打补丁的机器。顺序不能反。他手边那张排期表，还是上周三排的。
